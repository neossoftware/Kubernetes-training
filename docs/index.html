🐳 1.1 — ¿Qué es un Container y por qué existe? Semana 1 — Teoría
TeoríaEl problema que resuelven los containers

Antes de los containers existía el problema clásico: "En mi máquina funciona". La aplicación corría perfecto en el laptop del desarrollador pero fallaba en producción porque las versiones de Node, Java, librerías del sistema operativo o variables de entorno eran diferentes.

Las máquinas virtuales (VMs) resolvieron el aislamiento pero con un costo alto: cada VM incluye un sistema operativo completo (varios GBs), arrancan en minutos y consumen mucha RAM y CPU en overhead.

Los containers son una solución más liviana. En lugar de virtualizar el hardware completo, virtualizan solo el espacio de usuario del sistema operativo, usando dos características del kernel de Linux:

  • namespaces — aislan recursos: PID, red, filesystem, usuarios. Cada container tiene su propio árbol de procesos y su propia red.
  • cgroups (control groups) — limitan y miden el uso de recursos: cuánta CPU y RAM puede usar un container.

El resultado: containers arrancan en milisegundos, pesan megabytes y comparten el kernel del host. En el mismo servidor donde una VM correría 10 máquinas virtuales, puedes correr 100+ containers.

TeoríaImágenes vs Containers: la diferencia fundamental

Una imagen Docker es una plantilla de solo lectura que describe cómo debe ser el sistema de archivos de tu aplicación. Es inmutable — no cambia. Es como una clase en programación orientada a objetos.

Un container es una instancia en ejecución de una imagen — como un objeto instanciado de una clase. Puedes crear 100 containers del mismo imagen. Cada uno tiene su propia capa de escritura temporal (desaparece cuando el container se elimina).

Las imágenes se construyen en capas (layers) usando Union File System. Cada instrucción en el Dockerfile crea una capa. Las capas se cachean y se reusan entre imágenes, por eso los builds son rápidos después del primero.

  • FROM ubuntu:22.04 → capa base (descargada de Docker Hub)
  • RUN apt-get install nodejs → nueva capa con Node instalado
  • COPY . /app → nueva capa con tu código
  • CMD ["node","server.js"] → metadata de la imagen (no crea capa de filesystem)

Si cambias solo tu código (COPY . /app), Docker reutiliza las capas anteriores del cache. El build es instantáneo. Por eso el orden en el Dockerfile importa: primero lo que cambia menos, luego lo que cambia más.

⌨️ 1.2 — Comandos Docker Esenciales Semana 1 — Teoría + Práctica
TeoríaCiclo de vida de un container y sus comandos

Un container pasa por estados: Created → Running → Paused → Stopped → Removed. Cada estado tiene sus comandos.

  • docker run — crea y arranca un container en un solo comando. Con -d corre en background (detached). Con -p host:container mapea puertos. Con -e VAR=valor pasa variables de entorno. Con --name le da un nombre.
  • docker ps — lista containers corriendo. Con -a muestra también los detenidos.
  • docker logs NOMBRE — muestra stdout/stderr del container. Con -f hace follow (stream en tiempo real).
  • docker exec -it NOMBRE bash — abre una terminal interactiva dentro del container. Útil para debug.
  • docker stop NOMBRE — envía SIGTERM, espera 10s, luego SIGKILL. Graceful shutdown.
  • docker rm NOMBRE — elimina el container (debe estar detenido). Con -f fuerza.
  • docker images — lista imágenes descargadas localmente.
  • docker build -t nombre:tag . — construye imagen desde el Dockerfile del directorio actual.
  • docker inspect NOMBRE — detalles completos en JSON: IP, volúmenes, config, etc.
  • docker stats — uso de CPU, RAM, red en tiempo real de todos los containers.
TeoríaRedes Docker: cómo se comunican los containers

Docker crea una red virtual para los containers. Existen 3 drivers principales:

  • bridge (default) — red privada en el host. Los containers en la misma red bridge personalizada pueden comunicarse usando el nombre del container como hostname. La red bridge default (docker0) NO permite comunicación por nombre.
  • host — el container comparte la red del host directamente. Sin aislamiento de red. Útil para performance máxima.
  • none — sin red. Container completamente aislado.

La regla de oro: siempre crea una red personalizada (docker network create mi-red) y conecta tus containers ahí. Así se hablan por nombre. Con docker-compose esto es automático.

TeoríaVolúmenes: datos que persisten más allá del container

El filesystem de un container es efímero — cuando eliminas el container, los datos desaparecen. Para persistir datos existen dos mecanismos:

  • Bind mounts — montas un directorio del host dentro del container (-v /host/path:/container/path). Útil en desarrollo para live-reload. El container ve los cambios del host en tiempo real.
  • Named volumes — Docker gestiona el almacenamiento (-v mi-volumen:/container/path). Docker decide dónde guarda los datos en el host. Mejor para producción y bases de datos. Portable entre máquinas.

Para bases de datos siempre usa named volumes. Los datos de PostgreSQL/MySQL deben sobrevivir a recreaciones del container.

Ciclo de vida: stop, start, restart, pause, rm
# Detener gracefully (SIGTERM → espera 10s → SIGKILL)

Teoría¿Qué es un Dockerfile y cuáles son sus instrucciones clave?

Un Dockerfile es un script de instrucciones para construir una imagen. Las instrucciones más importantes:

  • FROM — imagen base. Siempre la primera instrucción. Usa imágenes -alpine o -slim para reducir tamaño.
  • WORKDIR — directorio de trabajo dentro del container. Equivale a mkdir + cd.
  • COPY — copia archivos del host al container. COPY src dst.
  • RUN — ejecuta comandos durante el build (instalar dependencias, compilar). Crea una nueva capa.
  • EXPOSE — documenta el puerto que escucha la app (no lo abre, solo documenta).
  • ENV — variables de entorno disponibles en build time y runtime.
  • CMD — comando por defecto cuando el container arranca. Se puede sobreescribir en docker run.
  • ENTRYPOINT — como CMD pero no se puede sobreescribir fácilmente. Útil para scripts de inicio.

Multi-stage builds: técnica para separar el entorno de compilación del de producción. El stage final solo incluye los artefactos necesarios (sin compilador, sin devDependencies). Reduce drásticamente el tamaño de la imagen.

TeoríaDocker Compose: orquestar múltiples servicios localmente

Docker Compose es una herramienta para definir y correr aplicaciones multi-container. En un solo archivo YAML (docker-compose.yml) describes todos los servicios, redes y volúmenes de tu aplicación.

  • services — cada servicio es un container. Tiene su propia config de imagen, puertos, variables de entorno, volúmenes y dependencias.
  • depends_on — define el orden de inicio. Con condition: service_healthy espera al healthcheck.
  • networks — Compose crea automáticamente una red para todos los servicios. Se hablan por nombre del servicio.
  • volumes — volúmenes nombrados compartidos entre servicios.

Comandos clave: docker compose up -d (levantar en background), docker compose logs -f (ver logs), docker compose down (bajar), docker compose down -v (bajar y eliminar volúmenes).

Al terminar tendrás los dos servicios corriendo con un solo comando: docker compose up --build.

Objetivos de aprendizaje

  • Escribir un Dockerfile multi-stage para Node.js (deps → build → prod)
  • Escribir un Dockerfile multi-stage para React (build → nginx serve)
  • Configurar Docker Compose con servicios, redes bridge y healthchecks
  • Entender cómo los contenedores se comunican por nombre de servicio dentro de una red Docker
  • Usar depends_on: condition: service_healthy para arranque ordenado

const express = require('express');
const cors    = require('cors');

const app  = express();
const PORT = process.env.PORT || 3000;

// Middleware
app.use(cors());
app.use(express.json());

// Base de datos simulada en memoria
let products = [
  { id: 1, name: 'Teclado Mecánico',  price: 89.99,  stock: 15 },
  { id: 2, name: 'Monitor Curvo',     price: 349.00, stock: 8  },
  { id: 3, name: 'Mouse Ergonómico',  price: 45.50,  stock: 22 },
  { id: 4, name: 'Laptop Stand',      price: 32.00,  stock: 40 },
];
let nextId = 5;

// ─── Rutas ───────────────────────────────────

// GET /api/hello — health check
app.get('/api/hello', (req, res) => {
  res.json({
    msg: '¡Hola desde Kubernetes Ninja Lab!',
    env: process.env.NODE_ENV || 'development',
    hostname: require('os').hostname(),
  });
});

// GET /api/products — listar productos
app.get('/api/products', (req, res) => {
  res.json({ data: products, total: products.length });
});

// GET /api/products/:id — obtener uno
app.get('/api/products/:id', (req, res) => {
  const product = products.find(p => p.id === parseInt(req.params.id));
  if (!product) return res.status(404).json({ error: 'Producto no encontrado' });
  res.json(product);
});

// POST /api/products — crear producto
app.post('/api/products', (req, res) => {
  const { name, price, stock } = req.body;
  if (!name || price === undefined) {
    return res.status(400).json({ error: 'name y price son requeridos' });
  }
  const product = { id: nextId++, name, price: parseFloat(price), stock: stock || 0 };
  products.push(product);
  res.status(201).json(product);
});

// PUT /api/products/:id — actualizar
app.put('/api/products/:id', (req, res) => {
  const idx = products.findIndex(p => p.id === parseInt(req.params.id));
  if (idx === -1) return res.status(404).json({ error: 'Producto no encontrado' });
  products[idx] = { ...products[idx], ...req.body, id: products[idx].id };
  res.json(products[idx]);
});

// DELETE /api/products/:id — eliminar
app.delete('/api/products/:id', (req, res) => {
  const idx = products.findIndex(p => p.id === parseInt(req.params.id));
  if (idx === -1) return res.status(404).json({ error: 'Producto no encontrado' });
  const deleted = products.splice(idx, 1)[0];
  res.json({ deleted });
});

// Arrancar servidor
app.listen(PORT, '0.0.0.0', () => {
  console.log(`🚀 API corriendo en puerto ${PORT}`);
});

  const [loading,  setLoading]  = useState(true);

  const [form,     setForm]     = useState({ name:'', price:'', stock:'' });
  const [info,     setInfo]     = useState(null);

    axios.get(`${API_URL}/api/hello`)
      .then(r => setInfo(r.data))
      .catch(() => {});

    setLoading(true);

      .catch(e => { setError(e.message); setLoading(false); });

TeoríaBuenas prácticas para dockerizar aplicaciones Java/Spring Boot

Dockerizar Java tiene particularidades importantes:

  • JDK vs JRE: usa JDK en el stage de build y JRE (o JRE-headless) en el stage final. La JRE es mucho más pequeña que el JDK completo.
  • eclipse-temurin — distribución OpenJDK de alta calidad de Adoptium. Preferir sobre openjdk oficial (menos mantenida).
  • Layered JARs: Spring Boot 2.3+ soporta JARs en capas (jarmode=layertools). Divide el JAR en: dependencies, spring-boot-loader, snapshot-dependencies, application. La capa de tu código (application) es la única que cambia en cada build — las demás capas son cacheadas por Docker.
  • Variables de entorno en Spring Boot: Spring Boot automáticamente convierte variables de entorno en propiedades. SPRING_DATASOURCE_URL → spring.datasource.url. Esto hace configuración 12-factor app muy fácil.
  • Spring Actuator: siempre incluirlo. Expone /actuator/health para healthchecks, /actuator/info y métricas.

import jakarta.persistence.*;
import jakarta.validation.constraints.*;
import lombok.*;

@Entity
@Table(name = "products")
@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NotBlank(message = "El nombre es requerido")
    @Size(max = 100)
    @Column(nullable = false)
    private String name;

    @NotNull
    @DecimalMin("0.0")
    @Column(nullable = false)
    private Double price;

    @Min(0)
    @Column(nullable = false)
    private Integer stock = 0;

    @Column(length = 500)
    private String description;
}

src/main/java/com/k8sninja/products/ProductController.java 
package com.k8sninja.products;

import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import java.util.List;
import java.util.Map;

@RestController
@RequestMapping("/api/products")
@CrossOrigin(origins = "*")
@RequiredArgsConstructor
public class ProductController {

    private final ProductRepository repo;

    // GET /api/products
    @GetMapping
    public ResponseEntity<Map<String,Object>> getAll(
            @RequestParam(required=false) String search) {
        List<Product> products = (search != null)
            ? repo.findByNameContainingIgnoreCase(search)
            : repo.findAll();
        return ResponseEntity.ok(Map.of(
            "data",  products,
            "total", products.size()
        ));
    }

    // GET /api/products/:id
    @GetMapping("/{id}")
    public ResponseEntity<Product> getOne(@PathVariable Long id) {
        return repo.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    // POST /api/products
    @PostMapping
    public ResponseEntity<Product> create(@Valid @RequestBody Product product) {
        product.setId(null); // Ignorar ID enviado
        return ResponseEntity.status(HttpStatus.CREATED).body(repo.save(product));
    }

    // PUT /api/products/:id
    @PutMapping("/{id}")
    public ResponseEntity<Product> update(@PathVariable Long id,
                                           @Valid @RequestBody Product product) {
        if (!repo.existsById(id)) return ResponseEntity.notFound().build();
        product.setId(id);
        return ResponseEntity.ok(repo.save(product));
    }

    // DELETE /api/products/:id
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        if (!repo.existsById(id)) return ResponseEntity.notFound().build();
        repo.deleteById(id);
        return ResponseEntity.noContent().build();
    }

    // GET /api/products/health
    @GetMapping("/health")
    public ResponseEntity<Map<String,String>> health() {
        long count = repo.count();
        return ResponseEntity.ok(Map.of(
            "status",   "UP",
            "products", String.valueOf(count)
        ));
    }
}

⚠️ Propiedades requeridas en application.properties
Para que Spring Boot ejecute data.sql correctamente debes agregar estas dos propiedades. Sin ellas verás el error "table products does not exist" porque Spring intenta correr el SQL antes de que Hibernate haya creado la tabla:

spring.jpa.defer-datasource-initialization=true
spring.sql.init.mode=always

defer-datasource-initialization obliga a Spring a esperar que Hibernate termine de crear el esquema antes de ejecutar el script SQL.

TeoríaAngular 21 — Signals, nueva sintaxis de templates y change detection

Angular es un framework TypeScript de Google para SPAs. Este lab usa Angular 21, que incorpora cambios importantes respecto a versiones anteriores que vale la pena entender:

  • Standalone Components (Angular 17+): Los componentes ya no necesitan NgModules. Se declaran con standalone: true e importan solo lo que usan (FormsModule, DecimalPipe).
  • Signals — el nuevo sistema reactivo: En Angular 17+ los signal<T>() reemplazan las propiedades simples para el estado del componente. Cuando llamas signal.set(valor), Angular detecta el cambio de forma inmediata y precisa, sin necesidad de Zone.js. Son la forma recomendada de manejar estado en Angular moderno.
  • Zone.js vs Signals — ¿por qué importa? Antes de Angular 17, Zone.js "parchaba" las APIs del navegador (XMLHttpRequest, setTimeout, Promises) para detectar cuando terminaba cualquier operación asíncrona y disparar re-render automático. Angular 17-21 genera proyectos sin Zone.js por defecto. Sin Zone.js, asignar this.loading = false en el callback de un HTTP response no notifica a Angular — el spinner se queda pegado hasta que un evento del DOM (click) fuerza un ciclo de change detection. Con Signals, ese problema no existe: this.loading.set(false) notifica a Angular directamente, sin Zone.js. Son dos soluciones alternativas al mismo problema — este lab usa Signals porque son el camino recomendado en Angular 17+: sin overhead de ~33KB extra y con actualización quirúrgica solo de los nodos del DOM que consumen el signal.
  • Nueva sintaxis de control flow (@if, @for): Angular 17+ reemplaza *ngIf y *ngFor con una sintaxis nativa del compilador. @if (cond) { ... } y @for (item of list; track item.id) { ... } son más eficientes, eliminan la necesidad de importar CommonModule y se integran con el sistema de Signals.
  • HttpClient: Se provee con provideHttpClient() en el appConfig. Retorna Observables — se usa .subscribe() para reaccionar a la respuesta.
  • Bootstrap 5: El JS de Bootstrap (modales, tooltips) se carga como script global en angular.json. El CSS se importa en styles.scss con @import 'bootstrap/scss/bootstrap' para que el builder de Angular lo procese.
  • Runtime config con env.js: En Angular el build es completamente estático. Para cambiar la URL de la API por entorno (dev/Docker/prod), se usa un archivo public/env.js que establece window.__env.API_URL antes de que Angular arranque. nginx sirve este archivo sin caché (Cache-Control: no-store) para que siempre esté fresco.
  • gzip en nginx: El bundle de Angular sin comprimir suma ~580KB (JS + CSS). Con gzip activado en nginx (gzip on; gzip_types text/css application/javascript) baja a ~140KB — reducción del 76% que mejora drásticamente el tiempo de carga inicial.

Crear el servicio ProductService
src/app/product.service.ts 
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Product, ProductsResponse } from './product.model';

@Injectable({ providedIn: 'root' })
export class ProductService {
  // Lee la URL de la API desde env.js (inyectado por nginx/Docker)
  private apiUrl = (window as any).__env?.API_URL ?? 'http://localhost:8080';

  constructor(private http: HttpClient) {}

  getAll(search?: string): Observable<ProductsResponse> {
    const params = search ? `?search=${encodeURIComponent(search)}` : '';
    return this.http.get<ProductsResponse>(`${this.apiUrl}/api/products${params}`);
  }

  getOne(id: number): Observable<Product> {
    return this.http.get<Product>(`${this.apiUrl}/api/products/${id}`);
  }

  create(product: Product): Observable<Product> {
    return this.http.post<Product>(`${this.apiUrl}/api/products`, product);
  }

  update(id: number, product: Product): Observable<Product> {
    return this.http.put<Product>(`${this.apiUrl}/api/products/${id}`, product);
  }

  delete(id: number): Observable<void> {
    return this.http.delete<void>(`${this.apiUrl}/api/products/${id}`);
  }
}

¿Qué es (window as any).__env? Es un objeto que Angular busca en el scope global del navegador. Lo populamos con un archivo env.js cargado antes del bundle de Angular. Esto nos permite cambiar la URL de la API sin recompilar.

src/app/app.ts 
import { Component, OnInit, ViewChild, ElementRef, signal } from '@angular/core';
import { FormsModule } from '@angular/forms';
import { DecimalPipe } from '@angular/common';
import { ProductService } from './product.service';
import { Product } from './product.model';

declare const bootstrap: any;

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [FormsModule, DecimalPipe],
  templateUrl: './app.html',
  styleUrl: './app.scss'
})
export class App implements OnInit {
  @ViewChild('productModal') modalRef!: ElementRef;

  // Signals — Angular detecta cambios automáticamente sin Zone.js
  products = signal<Product[]>([]);
  total = signal(0);
  loading = signal(false);
  error = signal('');
  saving = signal(false);
  formError = signal('');

  search = '';
  editingId: number | null = null;
  form: Product = { name: '', price: 0, stock: 0, description: '' };
  private modal: any = null;

  constructor(private svc: ProductService) {}

  ngOnInit(): void { this.load(); }

  load(): void {
    this.loading.set(true);
    this.error.set('');
    this.svc.getAll(this.search || undefined).subscribe({
      next: res => {
        this.products.set(res.data);
        this.total.set(res.total);
        this.loading.set(false);
      },
      error: () => {
        this.error.set('Error al cargar los productos. Verifica que la API esté activa.');
        this.loading.set(false);
      }
    });
  }

  openCreate(): void {
    this.editingId = null;
    this.form = { name: '', price: 0, stock: 0, description: '' };
    this.formError.set('');
    this.getModal().show();
  }

  openEdit(p: Product): void {
    this.editingId = p.id ?? null;
    this.form = { ...p };
    this.formError.set('');
    this.getModal().show();
  }

  save(): void {
    if (!this.form.name.trim()) { this.formError.set('El nombre es requerido.'); return; }
    if (this.form.price < 0 || this.form.stock < 0) { this.formError.set('Precio y stock deben ser valores positivos.'); return; }
    this.saving.set(true);
    const obs = this.editingId
      ? this.svc.update(this.editingId, this.form)
      : this.svc.create(this.form);
    obs.subscribe({
      next: () => { this.saving.set(false); this.getModal().hide(); this.load(); },
      error: () => { this.saving.set(false); this.formError.set('Error al guardar. Intenta de nuevo.'); }
    });
  }

  delete(p: Product): void {
    if (!confirm(`¿Eliminar "${p.name}"?`)) return;
    this.svc.delete(p.id!).subscribe({
      next: () => this.load(),
      error: () => this.error.set('Error al eliminar el producto.')
    });
  }

  private getModal(): any {
    if (!this.modal) this.modal = new bootstrap.Modal(this.modalRef.nativeElement);
    return this.modal;
  }
}

¿Por qué Signals en lugar de propiedades simples? Con this.loading = false (propiedad simple), Angular en versión 17+ no sabe que el estado cambió — el template no se actualiza hasta que ocurre un evento del DOM. Con this.loading.set(false) (signal), Angular recibe una notificación reactiva inmediata y repinta exactamente los nodos del DOM que consumen ese signal. Es más eficiente y no requiere Zone.js.

@ViewChild('productModal') obtiene la referencia al elemento del DOM del modal de Bootstrap para controlarlo desde TypeScript. Los Signals se leen en el template como funciones: loading(), products(), etc.

nginx.conf — SPA routing + gzip + caché

Angular en producción genera archivos estáticos. El nginx necesita: redirigir rutas desconocidas a index.html (SPA routing), comprimir con gzip, y aplicar caché larga a los assets hasheados:

angular-frontend/nginx.conf 
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Gzip — comprime JS/CSS antes de enviarlos al browser
    # Reduce el bundle de ~580KB a ~140KB (76% menos)
    gzip on;
    gzip_types text/html text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
    gzip_comp_level 6;

    # env.js sin caché — la URL de la API debe actualizarse en cada deploy
    location = /env.js {
        add_header Cache-Control "no-store, no-cache, must-revalidate";
        try_files $uri =404;
    }

    # SPA routing — rutas desconocidas van a index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Assets con hash en el nombre → caché de 1 año (immutable)
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}

¿Por qué try_files $uri $uri/ /index.html? Cuando el usuario navega directamente a /productos/5, nginx busca el archivo físico (no existe) y cae en el fallback: sirve index.html. Angular toma el control, lee la URL y renderiza la vista correcta.

¿Por qué gzip? El bundle de Angular incluye todo el framework + Bootstrap JS: ~580KB sin comprimir. Los navegadores modernos aceptan gzip y lo descomprimen instantáneamente. Con gzip_comp_level 6 (balance entre CPU y compresión) el total baja a ~140KB — mejora muy visible en la carga inicial, especialmente en redes móviles.

Troubleshooting — problemas comunes en este lab

Síntoma: el spinner se queda girando para siempre, los datos solo aparecen al hacer click

Este es el error más frecuente en Angular 17+. La causa: Angular generó el proyecto sin Zone.js por defecto, y el componente usaba propiedades simples (this.loading = false) en lugar de Signals. Sin Zone.js, Angular no sabe que el estado cambió cuando llega la respuesta HTTP — el template no se actualiza hasta que un evento del DOM (click) fuerza un ciclo de change detection.

Diagnóstico:

# ¿Zone.js está en polyfills?
grep "zone" angular.json

# ¿La API responde rápido? (si tarda aquí también, el problema es el backend)
curl -w "\nTiempo total: %{time_total}s\nPrimer byte: %{time_starttransfer}s\n" \
  -o /dev/null -s http://localhost:8080/api/products

Solución: usar Signals para todo el estado reactivo del componente. Zone.js NO es necesario si usas Signals — son mecanismos alternativos, no complementarios:

// ❌ Antes — Angular no detecta el cambio sin Zone.js
loading = false;
this.loading = false;   // callback HTTP: el template no se actualiza

// ✅ Después — Signal notifica a Angular directamente, sin Zone.js
loading = signal(false);
this.loading.set(false);  // callback HTTP: Angular re-renderiza inmediatamente

🏗️ 2.1 — Arquitectura de Kubernetes Semana 4 — Teoría + Setup
Teoría¿Qué es Kubernetes y qué problema resuelve?

Docker resolvió el problema de empaquetar aplicaciones. Pero imagina que tienes 50 microservicios corriendo en 20 servidores. ¿Quién decide en qué servidor corre cada container? ¿Qué pasa si un servidor falla? ¿Cómo escalas automáticamente cuando hay pico de tráfico? ¿Cómo haces un deploy sin downtime?

Kubernetes (K8s) es un sistema de orquestación de containers que automatiza el despliegue, escalado y gestión de aplicaciones containerizadas. Fue creado por Google, basado en su sistema interno Borg, y donado a la CNCF en 2014.

K8s piensa en términos de estado deseado vs estado actual. Tú le dices "quiero 3 réplicas de mi API" y K8s se encarga de que siempre haya 3, incluso si un servidor falla.

TeoríaControl Plane: el cerebro del cluster

El Control Plane (antes llamado Master) gestiona el estado del cluster. Sus componentes:

  • kube-apiserver — el único punto de entrada al cluster. Todo (kubectl, otros componentes) habla con el cluster a través de la API REST que expone. Valida y procesa todas las peticiones.
  • etcd — base de datos distribuida clave-valor donde K8s guarda TODO el estado del cluster. Si pierdes etcd sin backup, pierdes el cluster. Es el "source of truth".
  • kube-scheduler — decide en qué nodo (servidor) se crea cada Pod. Considera recursos disponibles, affinity rules, taints/tolerations. No crea los pods — solo decide dónde van.
  • kube-controller-manager — colección de controladores que vigilan el estado del cluster y actúan para llegar al estado deseado. Ejemplos: ReplicaSet controller (asegura el número correcto de pods), Node controller (detecta nodos caídos), Job controller.
  • cloud-controller-manager — integración con el proveedor cloud. Crea Load Balancers en GCP/AWS cuando pides un Service de tipo LoadBalancer.
TeoríaWorker Nodes: donde corren tus aplicaciones

Los nodos worker son los servidores donde corren tus containers. Cada nodo tiene:

  • kubelet — agente de K8s en cada nodo. Habla con el API Server, recibe instrucciones sobre qué pods correr y reporta el estado. Es el responsable de que los containers del pod corran según la especificación.
  • kube-proxy — mantiene las reglas de red en el nodo. Implementa el concepto de Services en K8s, redirigiendo el tráfico a los pods correctos usando iptables o IPVS.
  • Container Runtime — el motor que corre los containers. K8s usa la interfaz CRI (Container Runtime Interface). Los runtimes más comunes: containerd (default en la mayoría), CRI-O.
TeoríaNamespaces: aislamiento lógico dentro del cluster

Los Namespaces son una forma de dividir un cluster en múltiples espacios virtuales. Son útiles para:

  • Separar entornos: development, staging, production en el mismo cluster.
  • Separar equipos o proyectos: team-backend, team-frontend.
  • Aplicar Resource Quotas y Limits por namespace.
  • Aplicar RBAC (permisos) por namespace.

Namespaces por defecto de K8s: default (donde van tus apps si no especificas), kube-system (componentes del sistema), kube-public (configmaps públicos), kube-node-lease (heartbeats de nodos).

Los recursos dentro de un namespace se referencian por nombre corto (my-service). Entre namespaces se usa el DNS completo: my-service.other-namespace.svc.cluster.local.

TeoríaPod: la unidad mínima de K8s

Un Pod es el objeto más pequeño de K8s. Un pod encapsula uno o más containers que comparten:

  • Red: misma IP, mismo localhost. Si tienes 2 containers en un pod, se comunican por localhost.

🔌 Lab 2-2 — Services: exponer tu Pod con NodePort Semana 4 — Teoría + Lab
Teoría¿Qué problema resuelve un Service?

Los Pods son efímeros — pueden morir y renacer con una IP diferente cada vez. Si tu frontend habla directamente con la IP de un Pod, se rompe cada vez que el Pod se reinicia.

Un Service es un recurso de Kubernetes que actúa como una dirección estable frente a un grupo de Pods. No importa cuántas veces mueran y renazcan los Pods — el Service siempre apunta a los que estén vivos usando labels como selector.

Sin Service:  Frontend → 10.1.0.45 (Pod muere) → ❌ conexión rota
Con Service:  Frontend → hello-svc → 10.1.0.45
                                   → 10.1.0.67  (K8s balancea automáticamente)
                                   → 10.1.0.89
TeoríaTipos de Service
Tipo Alcance Cuándo usarlo
ClusterIP (default) Solo dentro del cluster Comunicación interna entre microservicios
NodePort Puerto fijo en cada nodo (30000–32767) Desarrollo local con minikube / Docker Desktop
LoadBalancer IP pública via cloud (GCP/AWS/Azure) Producción — exponer al internet
ExternalName Alias DNS a un servicio externo Apuntar a una DB externa o API de terceros

En este lab usaremos NodePort — es el tipo más simple para acceder desde el navegador en local sin necesitar un cloud provider.

TeoríaLabels y Selectors: cómo el Service encuentra el Pod

Un Service no conoce los Pods por nombre — los descubre por sus labels. Es como poner una etiqueta en una caja: el Service busca todas las cajas que tengan esa etiqueta y les manda tráfico.

📦 Pod — nginx-service.yaml

📦 2.3 — Pods, Deployments y Services Semana 4 — Teoría
TeoríaDeployment: la forma correcta de correr apps

Un Deployment describe el estado deseado de tu aplicación: qué imagen correr, cuántas réplicas, cómo hacer updates. El Deployment Controller vigila constantemente y reconcilia el estado actual con el deseado.

Los Deployments gestionan ReplicaSets (que a su vez gestionan Pods). Cuando haces un update de imagen, el Deployment crea un nuevo ReplicaSet y va migrando los pods gradualmente — ese es el Rolling Update.

  • spec.replicas — cuántos pods correr.
  • spec.selector — qué pods pertenecen a este Deployment (por labels).
  • spec.template — plantilla para crear los pods.
  • spec.strategy.type: RollingUpdate — actualización gradual sin downtime. maxSurge: pods extra durante update. maxUnavailable: pods que pueden estar caídos durante update.
  • resources.requests/limits — CPU y memoria mínima (requests) y máxima (limits). SIEMPRE especificarlos en producción.
TeoríaService: red estable para pods efímeros

Los pods tienen IPs que cambian constantemente. Un Service provee una IP estable y un nombre DNS que siempre apunta a los pods correctos (usando label selectors). Tipos:

  • ClusterIP (default) — IP virtual accesible solo dentro del cluster. Para comunicación interna entre microservicios. La más común.
  • NodePort — expone el Service en un puerto fijo de todos los nodos (30000-32767). Permite acceso externo básico. Solo para desarrollo/testing.
  • LoadBalancer — crea un Load Balancer en el cloud provider (GCP, AWS). IP pública. Costoso si se abusa (cada LB tiene costo). En producción se prefiere Ingress.
  • ExternalName — mapea el service a un nombre DNS externo. Para acceder a servicios fuera del cluster como si fueran internos.

El kube-proxy en cada nodo mantiene las reglas de iptables que implementan el balanceo de carga del Service entre los pods. El DNS del cluster (CoreDNS) registra automáticamente cada Service: nombre-servicio.namespace.svc.cluster.local.

TeoríaProbes: cómo K8s sabe si tu app está bien

K8s usa tres tipos de probes para verificar el estado de los containers:

  • livenessProbe — ¿el container está vivo? Si falla, K8s reinicia el container. Detecta deadlocks o estados irrecuperables.
  • readinessProbe — ¿el container está listo para recibir tráfico? Si falla, K8s lo quita del Service (no le manda tráfico) pero NO lo reinicia. Útil para apps que tardan en arrancar o que necesitan carga inicial.
  • startupProbe — para apps con arranque lento. Desactiva liveness y readiness hasta que pase. Evita que K8s mate el container antes de que termine de iniciar.

Tipos de prueba: httpGet (llama un endpoint HTTP), exec (ejecuta comando), tcpSocket (verifica que el puerto responde).

Teoría¿Qué es un Deployment?

En los labs anteriores creaste Pods directamente. El problema: si un Pod falla, nadie lo recupera. Un Deployment resuelve eso — describes el estado que quieres ("quiero 3 pods de nginx corriendo") y K8s se encarga de mantenerlo así para siempre.

El Deployment no crea los Pods directamente — crea un ReplicaSet, y el ReplicaSet crea y vigila los Pods. Si uno muere, el ReplicaSet crea otro inmediatamente.

Teoría¿Qué son las réplicas y para qué sirven?

Una réplica es una copia idéntica del mismo Pod corriendo al mismo tiempo. Tener 3 réplicas significa que hay 3 instancias de nginx funcionando en paralelo.

        - name: nginx
          image: nginx:1.27-alpine

apiVersion: v1

🔧 2.5 — ConfigMaps, Secrets y StatefulSets Semana 5 — Teoría + Lab
TeoríaConfigMap: externalizar configuración

Un ConfigMap almacena datos de configuración no sensibles como pares clave-valor. El principio de las 12-factor apps dicta que la configuración debe estar separada del código.

Formas de consumir un ConfigMap en un pod:

  • envFrom.configMapRef — inyecta todas las claves como variables de entorno.
  • env.valueFrom.configMapKeyRef — inyecta una clave específica como variable de entorno.
  • volumeMounts — monta el ConfigMap como archivos. Útil para archivos de configuración completos (nginx.conf, application.properties).

Limitación importante: cuando actualizas un ConfigMap, los pods existentes NO se reinician automáticamente (a menos que uses herramientas como Reloader). Con volúmenes, el archivo se actualiza eventualmente. Con envFrom, necesitas reiniciar el pod.

TeoríaSecret: datos sensibles en Kubernetes

Los Secrets son similares a los ConfigMaps pero para datos sensibles. Los datos se almacenan en base64 (no es encriptación — solo codificación). Por defecto, los Secrets en etcd NO están encriptados a menos que configures Encryption at Rest.

Tipos de Secrets:

  • Opaque — tipo genérico. Para cualquier dato sensible.
  • kubernetes.io/tls — certificados TLS (cert + key).
  • kubernetes.io/dockerconfigjson — credenciales de registro de Docker privado.
  • kubernetes.io/service-account-token — tokens de Service Accounts.

Buenas prácticas de seguridad: nunca los commitees en git en texto plano. Usa stringData en los YAMLs localmente pero agrega los archivos de Secret al .gitignore. En producción usa Sealed Secrets, External Secrets Operator, o integra con HashiCorp Vault / GCP Secret Manager.

TeoríaStatefulSet vs Deployment: cuándo usar cada uno

Un StatefulSet gestiona aplicaciones que necesitan identidad persistente. A diferencia de los Deployments:

  • Identidad estable: los pods se llaman nombre-0, nombre-1, nombre-2. Siempre el mismo nombre tras un reinicio.
  • Almacenamiento estable: cada pod tiene su propio PVC que persiste si el pod se elimina. Con Deployments, todos los pods comparten el mismo PVC.
  • Orden de despliegue: se crean y destruyen en orden determinístico (0 → 1 → 2, y al eliminar en orden inverso).
  • DNS estable: cada pod tiene su propio registro DNS: nombre-0.headless-svc.namespace.svc.cluster.local.

Cuándo usar StatefulSet: bases de datos (PostgreSQL, MySQL, MongoDB), sistemas de mensajería (Kafka, RabbitMQ), cualquier app que necesite identidad persistente por pod.

Cuándo usar Deployment: aplicaciones sin estado (stateless) como APIs REST, frontends, workers.

🌐 3.1 — Ingress Controller: el gateway de entrada Semana 6 — Teoría + Lab
Teoría¿Qué es Ingress y por qué es mejor que LoadBalancer?

Si tienes 10 microservicios y cada uno usa un Service de tipo LoadBalancer, tienes 10 IPs públicas y 10 facturas del cloud provider. Costoso y difícil de gestionar.

Un Ingress es un único punto de entrada HTTP/HTTPS al cluster que enruta el tráfico a diferentes Services según reglas (por path, por hostname). Un solo Load Balancer para todas tus apps.

El Ingress Controller es el componente que implementa las reglas del Ingress. El más popular es ingress-nginx (nginx como proxy reverso). Otros: Traefik, HAProxy, Kong, AWS ALB Ingress Controller.

El Ingress también puede manejar: terminación TLS (certificados SSL), rate limiting, autenticación básica, redirects, rewrites de URLs, CORS headers, y más — todo con anotaciones.

⚓ 3.2 — Helm: Package Manager de Kubernetes Semana 7-8 — Teoría + Lab
Teoría¿Qué es Helm y por qué lo necesitas?

Cuando tienes 15 archivos YAML para desplegar una app, gestionar versiones, environments (dev/prod con distintas configs) y upgrades se vuelve caótico. Helm resuelve esto.

Helm es el package manager de Kubernetes, similar a npm o apt. Un Chart es un paquete Helm que contiene todos los manifests K8s necesarios para desplegar una app, pero parametrizados con templates.

  • templates/ — archivos YAML con sintaxis de Go Templates. {{ .Values.replicas }} se reemplaza con el valor de values.yaml.
  • values.yaml — valores por defecto del chart. Se pueden sobreescribir en el install/upgrade.
  • Chart.yaml — metadata: nombre, versión, descripción.
  • _helpers.tpl — funciones y templates reutilizables.

Comandos clave: helm install, helm upgrade, helm rollback, helm uninstall, helm list, helm repo add.

Helm vs Kustomize: Helm usa templates (más potente pero más complejo). Kustomize usa overlays (más simple, viene incluido en kubectl). En producción muchos usan Helm para apps de terceros (PostgreSQL, nginx) y Kustomize o Helm para sus propias apps.

💾 4.1 — Storage en K8s: PV, PVC, StorageClass y StatefulSets Semana 9 — Teoría + Lab
TeoríaPersistentVolumes, PersistentVolumeClaims y StorageClass

El modelo de almacenamiento de K8s tiene 3 capas de abstracción:

  • PersistentVolume (PV) — el almacenamiento físico. Puede ser un disco de GCP, AWS EBS, NFS, o directorio local. Lo crea el admin del cluster o se crea dinámicamente.
  • PersistentVolumeClaim (PVC) — la solicitud de almacenamiento del developer. "Necesito 10GB ReadWriteOnce". K8s busca un PV compatible y lo "bindea".
  • StorageClass — define el tipo de almacenamiento y el provisioner. Permite provisionamiento dinámico: cuando creas un PVC, automáticamente se crea el PV. En GKE hay standard (HDD) y premium-rwo (SSD). En AWS hay gp2, gp3, io1.

Access Modes: ReadWriteOnce (un nodo puede leer/escribir — para DBs), ReadOnlyMany (múltiples nodos leen), ReadWriteMany (múltiples nodos leen/escriben — requiere NFS o almacenamiento especial).

volumeClaimTemplates en StatefulSets: la forma más elegante de dar a cada pod su propio PVC. En un StatefulSet con 3 réplicas y volumeClaimTemplates, K8s crea automáticamente data-db-0, data-db-1, data-db-2.

TeoríaQuarkus: Java nativo en containers

Quarkus es un framework Java diseñado para contenedores y Kubernetes. Sus ventajas sobre Spring Boot en K8s:

  • Modo nativo (GraalVM): compila la app a un binario nativo sin JVM. Startup en <50ms, consumo de memoria <50MB. Perfecto para microservicios.
  • Modo JVM: aún más rápido que Spring Boot en JVM gracias a build-time optimizations.
  • Kubernetes-native: Quarkus genera automáticamente los manifests K8s con quarkus-kubernetes extension. También tiene integración nativa con Keycloak, OpenTelemetry y más.
  • Dev Mode: quarkus dev tiene live reload instantáneo — sin reiniciar el server.

const app    = express();
const PORT   = process.env.PORT || 8084;
const REDIS  = process.env.REDIS_URL || 'redis://localhost:6379';

app.use(express.json());

let redisClient;
(async () => {
  redisClient = redis.createClient({ url: REDIS });
  redisClient.on('error', err => console.error('Redis error:', err));
  await redisClient.connect();
  console.log('✅ Conectado a Redis');
})();

// POST /api/notifications — encolar notificación
app.post('/api/notifications', async (req, res) => {
  const { userId, type, message } = req.body;
  const notification = {
    id: Date.now().toString(),
    userId, type, message,
    createdAt: new Date().toISOString(),
    status: 'queued'
  };
  // Guardar en Redis con TTL de 24 horas
  await redisClient.setEx(
    `notification:${notification.id}`,
    86400,
    JSON.stringify(notification)
  );
  // Push a lista de pendientes del usuario
  await redisClient.lPush(`user:${userId}:notifications`, notification.id);
  console.log(`📬 Notificación encolada: ${type} para usuario ${userId}`);
  res.status(202).json({ queued: true, id: notification.id });
});

// GET /api/notifications/:userId — obtener notificaciones
app.get('/api/notifications/:userId', async (req, res) => {
  const ids = await redisClient.lRange(`user:${req.params.userId}:notifications`, 0, 19);
  const notifications = await Promise.all(
    ids.map(async id => {
      const data = await redisClient.get(`notification:${id}`);
      return data ? JSON.parse(data) : null;
    })
  );
  res.json(notifications.filter(Boolean));
});

app.get('/health', (req, res) => res.json({ status: 'UP' }));

app.listen(PORT, () => console.log(`🔔 Notification Service en puerto ${PORT}`));

🏗️ 6.1 — Terraform: Infraestructura como Código para GKE Semana 14
Teoría¿Qué es Terraform y por qué usarlo para crear clusters?

Terraform de HashiCorp es la herramienta estándar de Infrastructure as Code (IaC). En lugar de crear el cluster desde la consola de GCP o con comandos CLI, defines la infraestructura en archivos .tf que son versionables, reproducibles y auditables.

  • Provider — plugin que habla con el cloud provider (google, aws, azurerm).
  • Resource — un componente de infraestructura (cluster, node pool, VPC).
  • Variable — parámetros configurables del código.
  • Output — valores que exporta Terraform (ej: endpoint del cluster).
  • State (terraform.tfstate) — Terraform guarda el estado de la infra. Nunca lo borres. En equipos se guarda en GCS o S3.

Comandos clave: terraform init (descarga providers), terraform plan (preview de cambios), terraform apply (aplicar), terraform destroy (destruir — ¡costo!).

TeoríaGitOps: el paradigma moderno de despliegue

GitOps es un modelo operacional donde el estado deseado de la infraestructura y las aplicaciones se define en Git. Un operador (ArgoCD, Flux) compara continuamente el estado en Git con el estado real del cluster y reconcilia las diferencias.

Flujo GitOps:

  • Developer hace push de código → CI construye imagen y actualiza el tag en el repo de manifests K8s.
  • ArgoCD detecta el cambio en el repo de manifests → aplica los cambios al cluster automáticamente.
  • Resultado: el cluster siempre refleja lo que está en Git. Si alguien hace cambios manuales con kubectl, ArgoCD los revierte.

ArgoCD tiene una UI visual que muestra el estado de sync de cada app, el árbol de recursos K8s, diffs entre estado deseado y actual, y permite rollbacks.

TeoríaLos tres pilares de la observabilidad

Para entender qué está pasando en tu cluster en producción necesitas tres tipos de datos:

  • Métricas (Prometheus) — valores numéricos a lo largo del tiempo. CPU, memoria, latencia de requests, tasa de errores. Prometheus hace scraping (polling) de los endpoints /metrics de tus apps cada 15-30 segundos.
  • Logs (Loki) — registros de eventos. Qué pasó y cuándo. Loki es como Prometheus pero para logs — los indexa por labels, no por contenido (más eficiente y barato que Elasticsearch).
  • Trazas (Tempo/Jaeger) — seguimiento de una request a través de múltiples microservicios. "¿Cuánto tardó cada servicio en procesar esta petición?"

Grafana unifica la visualización de los tres. Un solo dashboard puede mostrar métricas, logs y trazas correlacionadas para el mismo período de tiempo.

TeoríaOAuth2 y OpenID Connect: el estándar de autenticación moderno

OAuth2 es un protocolo de autorización. Permite que una aplicación obtenga acceso limitado a los recursos de un usuario en otro servicio sin necesidad de compartir la contraseña.

OpenID Connect (OIDC) es una capa de identidad sobre OAuth2. Agrega autenticación: además del access token, devuelve un ID token con información del usuario.

Flujo para SPAs con backend (Authorization Code Flow + PKCE):

  • 1. React redirige al usuario a Keycloak con un code_challenge.
  • 2. Usuario ingresa credenciales en Keycloak (no en tu app).
  • 3. Keycloak redirige de vuelta con un authorization_code.
  • 4. React intercambia el code por tokens (access_token + refresh_token + id_token).
  • 5. React envía el access_token en el header Authorization: Bearer TOKEN en cada request a la API.
  • 6. Spring Boot valida el JWT sin llamar a Keycloak — solo verifica la firma con la clave pública.

Keycloak es el Identity Provider (IdP) de código abierto más popular. Soporta OAuth2, OIDC, SAML2. Maneja usuarios, roles, grupos, social login, MFA, etc.

TeoríaSpring Cloud Config: configuración centralizada

Spring Cloud Config Server centraliza la configuración de todos los microservicios en un repositorio Git. En lugar de tener un application.yml en cada microservicio, todos consultan el Config Server al arrancar.

  • El Config Server sirve configuración por application name y profile: product-service-k8s.yml.
  • Cuando actualizas el config en Git, puedes hacer POST /actuator/refresh para que el microservicio recargue la config sin reiniciar (con Spring Cloud Bus + Kafka/RabbitMQ se hace automáticamente).
  • Permite tener configs distintas por environment: product-service-dev.yml, product-service-prod.yml.

package com.k8sninja.products.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.oauth2.server.resource.authentication.*;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.config.Customizer;

import java.util.*;
import java.util.stream.Collectors;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s ->
                s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/**").permitAll()
                .requestMatchers("GET", "/api/products/**").permitAll()
                .requestMatchers("POST", "/api/products/**").hasRole("ADMIN")
                .requestMatchers("PUT", "/api/products/**").hasRole("ADMIN")
                .requestMatchers("DELETE", "/api/products/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 ->
                oauth2.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter())))
            .build();
    }

    // Convertir roles de Keycloak al formato de Spring Security
    @Bean
    public JwtAuthenticationConverter jwtConverter() {
        JwtGrantedAuthoritiesConverter converter = new JwtGrantedAuthoritiesConverter();
        converter.setAuthoritiesClaimName("realm_access.roles");
        converter.setAuthorityPrefix("ROLE_");

        JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();
        jwtConverter.setJwtGrantedAuthoritiesConverter(jwt -> {
            // Extraer roles del claim realm_access
            Map<String, Object> realmAccess =
                jwt.getClaim("realm_access");
            if (realmAccess == null) return List.of();

            @SuppressWarnings("unchecked")
            List<String> roles = (List<String>) realmAccess.get("roles");
            if (roles == null) return List.of();

            return roles.stream()
                .map(r -> new SimpleGrantedAuthority("ROLE_" + r.toUpperCase()))
                .collect(Collectors.toList());
        });
        return jwtConverter;
    }
}

import { useKeycloak } from '@react-keycloak/web';
import axios from 'axios';
import { useMemo } from 'react';

const API_URL = import.meta.env.VITE_API_URL || '/api';

export function useApi() {
  const { keycloak } = useKeycloak();

  const api = useMemo(() => {
    const instance = axios.create({ baseURL: API_URL });

    // Inyectar token JWT en cada request automáticamente
    instance.interceptors.request.use(config => {
      if (keycloak.token) {
        config.headers.Authorization = `Bearer ${keycloak.token}`;
      }
      return config;
    });

    // Auto-refresh token si expiró
    instance.interceptors.response.use(
      res => res,
      async err => {
        if (err.response?.status === 401) {
          await keycloak.updateToken(30);
          err.config.headers.Authorization = `Bearer ${keycloak.token}`;
          return axios(err.config);
        }
        return Promise.reject(err);
      }
    );

    return instance;
  }, [keycloak]);

  return { api, keycloak };
}
